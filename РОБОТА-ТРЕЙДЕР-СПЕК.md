# Вкладка «Робота» · трейдер — функціональна перебудова

Не про вигляд. Про те, що вкладка робить, які дані тримає і в якому порядку
проводить трейдера через день.

---

## 1. Що не так із поточною версією

Зараз вкладка — це **вітрина**: смужка рахунків, три числа, список джерел і
сітка з трьох кнопок (Журнал / Статистика / Калькулятор). Вона показує
результат і дає посилання. Вона нічого не **вимагає** і ні в чому не
**заважає**.

Наслідки, які видно з коду:

- **Калькулятор ізольований.** Він рахує лот, але результат нікуди не йде —
  його треба переписати руками в угоду. Тому ним і не користуються: дешевше
  порахувати в голові.
- **`followedPlan` нема з чим звіряти.** Поле в `Trade` є, але «план»
  ніде не існує як об'єкт. Відповідь «чи дотримався плану» ставиться по
  пам'яті через годину після виходу — і тому завжди «так».
- **Скріни зберігаються, але не в той момент.** `screenshots: string[]`
  заповнюється при розборі. Скрін *до входу* — з розміткою, за якою ти
  збирався торгувати — не зберігається ніде, а саме він відповідає на
  питання «а що я взагалі бачив».
- **Теги — це не сетапи.** `JournalTag` («OB», «FVG», «CHoCH») — плоский
  список ярликів без правил і без статистики. Питання «яка модель заробляє»
  не має відповіді, бо модель не описана.
- **Ризику нема як поняття.** Ні ліміту дня, ні ліміту на угоду, ні
  максимальної кількості угод. Додаток не може сказати «стоп», бо не знає
  правил.

Коротко: журнал відповідає на «що сталося». Не відповідає на «що я
збирався зробити» і «чи я порушив себе».

---

## 2. Нова організуюча ідея: торговий день

Вкладка перестає бути меню й стає **днем**. У дня три стани, і екран
показує рівно той, у якому ти зараз:

| Стан | Коли | Що на екрані |
|---|---|---|
| **До ринку** | план дня не закритий, відкритих позицій нема | ідеї на сьогодні, ліміти дня, чек-лист готовності |
| **У ринку** | є хоч одна відкрита позиція | позиції, ризик на столі, відстань до стопу, скільки ліміту з'їдено |
| **Після** | позицій нема, за сьогодні були угоди | розбір дня: що за планом, що ні, підсумок |

Стан визначається даними, а не перемикачем: `openTrades.length > 0` →
«у ринку»; інакше якщо є закриті угоди з сьогоднішньою датою → «після».

Це головна зміна. Усе інше — наслідки.

## 3. Нові сутності

### 3.1 `TradeIdea` — план угоди до входу

Новий стор `trade-plan-store.ts`.

```ts
export type IdeaStatus = "planned" | "taken" | "invalidated" | "missed";

export interface TradeIdea {
  id: string;
  date: string;              // день, на який планується
  accountId: string | null;
  instrumentId: string;
  direction: TradeDirection;
  setupId: string | null;    // з плейбука
  entry: number;             // рівень входу, що планується
  stop: number;
  take: number;
  /** Порахований розмір позиції — саме те, чого зараз бракує:
   *  калькулятор пише сюди, а не в порожнечу. */
  plannedLot: number;
  riskAmount: number;        // у валюті рахунку
  riskPct: number;
  /** Скрін розмітки ДО входу. Окреме поле, не спільний масив із
   *  розбором: питання «що я бачив» і «як вийшло» — різні питання, і
   *  зсипати обидві відповіді в один масив означає втратити перше. */
  planScreenshot?: string;
  note: string;              // умова входу словами: «чекаю ретест 1.0850»
  status: IdeaStatus;
  /** Заповнюється, коли ідея стала угодою — зв'язок план↔факт. */
  tradeId?: string;
  createdAt: string;
}
```

**Навіщо `invalidated` і `missed` окремо.** Ідея, яка не спрацювала за
ринком, і ідея, яку ти проґавив, — це різні помилки. Перша нормальна, друга
про виконавчу дисципліну. Якщо не розділити, обидві зникнуть як «не
торгував».

### 3.2 `Setup` — плейбук замість тегів

Новий стор `playbook-store.ts`. Сетап — окрема сутність із правилами.

```ts
export interface Setup {
  id: string;
  name: string;              // назву пише трейдер, додаток не пропонує
  /** Нейтральна класифікація — до якого класу поведінки ринку належить
   *  модель. Потрібна для статистики: «розвороти в мене не працюють» —
   *  це висновок, який неможливо зробити, якщо всі моделі плоскі. */
  kind: SetupKind;
  /** Умови, які мають збігтися. Чек-лист, а не опис — його видно перед
   *  входом і його треба відмітити. */
  checklist: string[];
  /** Сесії, у які цей сетап дозволений. Порожньо = будь-коли. */
  sessionIds: string[];
  instrumentIds: string[];   // порожньо = будь-який інструмент
  minRR: number;             // мінімальне співвідношення, нижче — порушення
  isArchived: boolean;
}
```

Статистика по сетапу рахується з угод, а не зберігається: вінрейт, середній
R, expectancy, profit factor, найгірша серія.

### 3.2.1 ICT-теги прибираються

Поточний посів `journal-config-store` — `OB`, `FVG`, `CHoCH`, `BOS`,
`Breaker Block`, `Liquidity Grab`. Це словник однієї конкретної методики,
зашитий у додаток як даність. Проблеми з ним три:

- він **нав'язує чужу школу** — трейдер, який працює по обʼємах або по
  ринковому профілю, відкриває журнал і бачить чужі терміни;
- він **не класифікує** — шість ярликів одного рівня без ієрархії, тому
  на їх основі не будується жодне зведення;
- він **описує вхід, а не поведінку ринку** — «OB» не каже, це був
  розворот чи продовження, а саме цей розріз дає висновки.

Замість нього — **два незалежні поля**, які відповідають на різні питання:

**1. `SetupKind` — що робив ринок** (на сетапі, не на угоді):

```ts
export type SetupKind =
  | "trend"       // продовження руху
  | "reversal"    // розворот
  | "breakout"    // пробій рівня / діапазону
  | "range"       // робота в діапазоні
  | "news"        // подія в календарі
  | "other";
```

Шість класів, які не належать жодній методиці. Своя модель називається як
завгодно — «ретест азійського максимуму», — але лягає в один із класів.

**2. `ExecutionMarker` — що робив трейдер** (на угоді):

```ts
export type ExecutionMarker =
  | "early_entry"      // зайшов до підтвердження
  | "late_entry"       // зайшов після відпрацювання
  | "moved_stop"       // рухав стоп проти себе
  | "manual_close"     // закрив руками до стопу/тейку
  | "no_take"          // вийшов раніше цілі
  | "oversize"         // розмір більший за план
  | "revenge"          // відігравався після збитку
  | "chased";          // догнав рух, що вже пішов
```

Це те, чого немає в жодному брокерському звіті й що не виводиться з цін.
Маркери множинні, ставляться при закритті, і **саме вони дають найцінніший
розріз статистики**: середній R угод без маркерів проти угод із маркерами.

Причина розділення: «яка модель працює» і «як я її псую» — два різні
питання. Один список тегів на обидва змішує їх у кашу, і саме тому теперішні
теги нічого не пояснюють.

Міграція: існуючі теги не видаляються з даних (це зіпсувало б історію), а
переносяться в `isCustom` теги користувача. Посів нових акаунтів — порожній.

### 3.3 `RiskRules` — правила, за якими додаток може сказати «стоп»

Розширення `personal-trading-accounts-store` / `prop-accounts-store` — правила
живуть на рахунку, бо для проп-акаунта вони інші, ніж для особистого.

```ts
export interface RiskRules {
  maxRiskPctPerTrade: number;   // 1.5
  maxDailyLossPct: number;      // 3 — далі день закритий
  maxTradesPerDay: number;      // 3
  /** Після скількох збитків поспіль додаток пропонує зупинитися. */
  tiltAfterLosses: number;      // 2
  /** Дозволені сесії. Угода поза ними — порушення. */
  allowedSessionIds: string[];
}
```

**Важливо:** правила — це не блокування. Додаток не має механізму завадити
відкрити угоду на біржі, і вдавати, що має, — самообман. Він фіксує
порушення й показує його на екрані дня та в тижневому розборі. Цінність у
тому, що порушення стає **видимим числом**, а не спогадом.

### 3.4 `DayLog` — підсумок дня

Не окремий стор: обчислюється з угод + ідей + правил. Але одне поле треба
зберігати — суб'єктивне:

```ts
export interface DayReview {
  date: string;
  accountId: string | null;
  /** Стан перед торгівлею: виспаний / втомлений / на емоціях. Одне з
   *  небагатьох, що корелює з результатом і чого нізвідки не імпортувати. */
  condition: "good" | "ok" | "poor" | null;
  note: string;
  closedAt: string;
}
```

## 4. Екрани

### 4.1 Головний екран вкладки — «Сьогодні»

Замість сітки модулів. Зверху смужка рахунків лишається (вона працює).

**Стан «До ринку»:**

1. **Ліміти дня** — скільки угод дозволено, скільки ризику лишилось,
   у якій сесії ти зараз. Три числа, які змінюються протягом дня.
2. **Ідеї на сьогодні** — список `TradeIdea` зі статусом `planned`.
   Кожна: інструмент, напрямок, рівень, R:R, порахований лот. Тап →
   «взяв» / «скасувалась» / «проґавив».
3. **Кнопка «Нова ідея»** — форма плану (див. 4.2).
4. Якщо ідей нема — не порожній екран, а питання: «Що дивишся сьогодні?»

**Стан «У ринку»:**

1. **Ризик на столі** — сума ризику всіх відкритих позицій у валюті й у
   відсотках рахунку. Одне число, якого зараз нема ніде.
2. **Позиції** — кожна з відстанню ціни до стопу й до тейку (потребує
   поточної ціни — див. 6. Відкриті питання).
3. **Скільки ліміту з'їдено** — денний P&L проти `maxDailyLossPct`.

**Стан «Після»:**

1. **Підсумок дня**: P&L, кількість угод, скільки за планом.
2. **Порушення** — список конкретних: «угода #3 при ліміті 3»,
   «ризик 2.4% при ліміті 1.5%», «вхід поза сесією».
3. **Розбір** — по кожній угоді: чи була ідея, чи збігся вхід із планом,
   скрін після. Плюс `DayReview.condition` і нотатка.

### 4.2 Форма плану = калькулятор

Калькулятор перестає бути окремою сторінкою. Він **стає формою нової ідеї**:
вибираєш інструмент, вводиш вхід/стоп/тейк — лот і ризик рахуються самі, R:R
показується одразу, і все це зберігається як `TradeIdea`.

Обґрунтування: ізольований калькулятор не використовують, бо результат треба
переносити руками. Той самий розрахунок усередині кроку, який усе одно
робиться, використовуватимуть завжди.

Порядок полів навмисно **вхід → стоп → тейк → ризик %**, а не «депозит →
ризик → пункти»: трейдер думає рівнями на графіку, а не пунктами.

### 4.3 Журнал — лишається, але зв'язується з планом

Форма закриття угоди отримує:
- прив'язку до `TradeIdea` (якщо була) — автоматично, якщо ідея відкрита на
  цьому ж інструменті й напрямку;
- питання «за планом?» **із контекстом**: поруч показується, що саме
  планувалось, тому відповідь перестає бути формальністю;
- скрін «після» окремо від скріна «до».

### 4.4 Календар угод

Окремий екран вкладки — місячна сітка. **Клітинка дня показує кількість
угод**, не суму.

Обґрунтування вибору: календар із сумами відповідає на «скільки я заробив у
вівторок», а це питання вже закрите кривою капіталу й підсумком дня.
Календар із кількістю відповідає на питання, яке більше ніде не видно —
**яка в мене частота і де вона зривається**. Три угоди в понеділок і сім у
четвер — це видно з першого погляду, і сім у четвер майже завжди означає
відігравання.

Клітинка:
- велика цифра — кількість закритих угод;
- порожній день лишається порожнім, не нулем (нуль читається як результат,
  а не як «не торгував»);
- тонка позначка в кутку, якщо в дні було порушення лімітів — дисципліна
  видима на рівні місяця, а не тільки дня;
- тап → день у «Розборі».

Під сіткою — рядок місяця: торгових днів, усього угод, середньо на день,
найбільша серія днів поспіль.

> Якщо згодом захочеш заливку за P&L — це один прапорець у налаштуваннях
> екрана, дані вже є. Свідомо не вмикається за замовчуванням: колір за
> знаком перетягує увагу на результат і повертає календар до питання, на
> яке вже є відповідь деінде.

### 4.5 Статистика — перебудова навколо сетапів

Зараз статистика по всіх угодах разом. Стає:
- **по сетапах** і **по класах** (`SetupKind`);
- **за планом vs проти плану** — два набори тих самих чисел поруч. Це
  найцінніший розріз: зазвичай виявляється, що система працює, а руки ні;
- **по маркерах виконання** — середній R угод із кожним маркером проти
  базового. Відповідає на «скільки мене коштує звичка рухати стоп»;
- **по сесіях** і **по днях тижня**;
- **крива капіталу** окремо для угод за планом.

### 4.6 Глибокі метрики

Те, чого немає в аматорських журналах. Усе рахується з наявних даних, нових
полів не потребує (крім MAE/MFE — див. нижче).

| Метрика | Формула | Що каже |
|---|---|---|
| **Expectancy** | `avg(R)` по всіх закритих | скільки R приносить середня угода. Єдине число, яке можна множити на кількість угод і прогнозувати |
| **Profit factor** | `сума прибутків / сума збитків` | <1 — система збиткова, скільки б не був вінрейт |
| **Payoff ratio** | `avg(виграш) / avg(програш)` | разом із вінрейтом дає повну картину: 40% вінрейту при payoff 3.0 краще за 70% при 0.4 |
| **Максимальна просадка** | пік→дно кривої капіталу | у грошах і у відсотках |
| **Найдовші серії** | поспіль виграшів / програшів | серія програшів — це те, під що треба мати капітал |
| **Розподіл R** | гістограма по кошиках | видно, чи є «товстий хвіст» великих збитків, який середні числа ховають |
| **Стандартне відхилення R** | σ по R | стабільність. Дві системи з однаковим expectancy й різною σ — різні системи |
| **Час у ринку** | середня тривалість угоди | окремо для виграшних і збиткових. Класична патологія: збиткові тримаються втричі довше |
| **MAE / MFE** | максимальна просадка й прибуток усередині угоди | відповідає на «мій стоп завеликий?» і «я виходжу зарано?» |

**Про MAE/MFE окремо.** Ці дві потребують даних, яких у нас нема: скільки
ціна ходила проти й за позицією *усередині* угоди. Біржі це не віддають у
closed-pnl. Варіанти: (а) не рахувати; (б) вводити руками при розборі —
два числа, які трейдер бачить на графіку; (в) тягнути свічки за період
угоди й рахувати. Пропозиція: **(б)**, з позначкою «необов'язково». (в) —
окрема інфраструктура заради двох чисел.

### 4.7 Тиждень

Окремий екран (або секція), що збирається щонеділі: P&L, дисципліна у
відсотках, найкращий і найгірший сетап, скільки ідей стало угодами.

### 4.8 Експорт і звітність

**CSV** — повне вивантаження угод з усіма полями, включно з планом, сетапом,
маркерами й порушеннями. Не «експорт для краси»: це страховка від того, що
дані живуть у localStorage одного пристрою.

**Місячний звіт (PDF)** — те, що можна показати проп-фірмі, інвестору або
наставнику:
- шапка: період, рахунок, стартовий і кінцевий баланс;
- крива капіталу й просадка;
- таблиця метрик із 4.6;
- розбивка по сетапах і класах;
- дисципліна: відсоток угод за планом, список порушень лімітів;
- **без скрінів і без особистих нотаток** — вони для себе, не для звіту.

Генерується на клієнті, щоб журнал не треба було нікуди відправляти.

---

## 5. Що видаляється

- **Сторінка `/work/calculator`** — переїжджає у форму ідеї.
- **Сітка «Модулі»** — замінюється станом дня.
- **Список «Джерела»** на головному екрані — переїжджає в налаштування
  журналу. Статус підключення бірж не те, що треба бачити щодня.
- **Три числа (вінрейт / сер. R / угод) у поточному вигляді** — вони
  описують «взагалі», а не «сьогодні». Переїжджають у статистику.

## 6. Відкриті питання — треба рішення

1. **Поточна ціна для відкритих позицій.** Без неї «відстань до стопу» не
   порахувати. Варіанти: (а) тягнути ціну з підключеної біржі — працює
   тільки для Bybit/OKX/Binance і не для MT5; (б) не показувати відстань,
   показувати лише запланований ризик; (в) оновлювати ціну раз на N хвилин
   лише коли екран відкритий. **Пропозиція: (б) на першому етапі**, бо
   ризик у грошах відомий одразу, а котирування — це окрема інфраструктура
   з лімітами й помилками.

2. **Чи мають ідеї жити довше за день.** Свінг-сетап може чекати тиждень.
   Пропозиція: поле `date` — це день, коли ідея *актуальна з*, і ідея не
   зникає, доки її не закрили руками, але в «Сьогодні» підсвічуються тільки
   релевантні.

3. **Автоматичне зв'язування ідеї з імпортованою угодою.** Для угод із
   біржі можна зіставляти за інструментом + напрямком + часом. Ризик
   помилкового збігу є. Пропозиція: пропонувати зв'язок, підтверджує
   людина — мовчазне зв'язування зіпсує статистику дисципліни, а це
   найцінніше, що тут є.

4. **Проп-акаунти й правила.** У проп-фірми свої ліміти (денна просадка,
   загальна). Їх треба вводити руками чи вивести з `maxDrawdown`, який уже
   є в `PropAccount`? Пропозиція: успадковувати з полів проп-акаунта, дати
   можливість перекрити.

## 7. Порядок робіт

| Етап | Що | Чому саме тут |
|---|---|---|
| 1 | Прибрати ICT-посів, `SetupKind` + `ExecutionMarker` | найдешевше і розблоковує статистику |
| 2 | `playbook-store` + екран сетапів | усе інше на нього посилається |
| 3 | Календар угод | працює вже на наявних даних, нічого не чекає |
| 4 | `trade-plan-store` + форма ідеї (= калькулятор) | дає об'єкт «план», без якого дисципліна не існує |
| 5 | Головний екран зі станами дня | видима частина, спирається на 2 і 4 |
| 6 | `RiskRules` + виявлення порушень | потребує ідей і угод разом |
| 7 | Зв'язок ідея↔угода у формі закриття | замикає цикл |
| 8 | Глибокі метрики + перебудова статистики | має сенс лише коли накопичились дані |
| 9 | Експорт CSV + місячний звіт | останнім, збирає все |

Етапи 1–3 дають користь одразу і не залежать ні від чого. 4–7 будують цикл
план→факт. 8–9 — те, заради чого все затівалось.

## 8. Що це змінює по суті

Зараз вкладка відповідає на одне питання: **скільки я заробив**.

Після перебудови вона відповідає на чотири:
- що я збираюся зробити сьогодні і яким розміром;
- скільки ризику зараз на столі;
- чи я зробив те, що збирався;
- яка з моїх моделей насправді працює.

Перше й третє — те, чого не дає жоден брокерський звіт, бо їх немає в
даних біржі. Вони існують тільки якщо їх записати до входу.
